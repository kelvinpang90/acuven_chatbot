## 1. 背景与目标

现在有两份顾客侧代码：

- `ai_chatbot_demo`（本仓库，后端约 1.68 万行）：给潜在客户看的行业演示。五个行业机器人、工具调用、图片/语音/文件、导演台、演示数据每晚重置、把 demo 号上的对话推给 CRM 收件箱（J-04）。
- `acuven_aichat`（约 1,160 行）：公司真实 WhatsApp 客服。WhatsApp Business App 与 Cloud API 共存（coexistence）、同事在手机 App 回复后 AI 自动让位、管理指令、白名单、原始同步数据落盘。代码基本完成，卡在 Meta 手续（App Review、Access Verification、备用号）。

两边约一半功能重复。E-21 定：以本仓库为底并入 aichat，改名后成为**唯一的顾客侧 AI Chatbot 产品**，同一份代码分 Demo、生产两套部署。

**目标**：一个服务同时满足两种用法（第 3 节），按租户配置，Acuven 自己是其中一个租户；行业演示照旧可演。

## 2. 范围

**做**：

- 面向终端顾客的对话：WhatsApp 与网页聊天窗口两类渠道。
- 租户、渠道、机器人、已接入系统、人工接手、身份核验的配置（首期由 Acuven 人员配置）。
- 业务系统按「客服接入契约」把能力开放给机器人。
- 三种人工接手方式。
- 模型用量上报 `ai_billing_hub`。
- 行业演示作为 Demo 实例继续运行。

**不做**（写明是为了验收时不被当成缺陷）：

| 不做 | 依据 |
| --- | --- |
| 员工侧、经营侧 AI 助手 | E-01、E-17：那是 `ai_billing_hub` 的 AI API |
| 工单（分派、状态流转、SLA、工单报表） | E-21 建议、A-15 未定：自带工作台只做对话接手与回复 |
| 客户自助配置后台（开户、改知识、改能力开关） | E-21 ⑧、B-02、G-02：后续能力，阶段 4 |
| 经 Chatbot 调用 `ai_billing_hub` 的 AI API 去调模型 | E-17：Chatbot 仍自己调模型，只上报用量 |
| 为某个业务系统在 Chatbot 里写专门的对接代码（阶段 3 迁完以后） | E-21 建议：一律走接入契约 |
| 真实收款、真实退款 | 网店是公开演示（H-01）；生产租户的退款等高风险写入只能「提出」，由有权人员确认（E-05） |

## 3. 两种用法

**U1 Acuven 公司客服**：Acuven 的客服 WhatsApp 号（coexistence，同事同时用手机 App）与官网等处的网页聊天窗口，回答公司、产品、价格、演示预约类问题，答不了或顾客要求时转人工。跑在生产实例上，Acuven 是一个租户。

**U2 嵌进业务系统**：CRM、ERP、网店、Inventory（现为 Stock Core 生产实例的平台渠道能力，C-21）及以后的项目，各自把能力（查订单、查库存、建线索……）按接入契约开放出来；Chatbot 用该系统的数据与功能服务**该系统的终端顾客**（网店的买家、ERP 客户的客户……）。系统的使用方（Acuven 或买了该系统的客户）就是租户。

两种用法共用同一套代码路径：U1 只是「没有接业务系统、或接得少」的租户，不走特殊分支。

## 4. 用词

| 词 | 含义 |
| --- | --- |
| 实例 | 一套部署（一份配置、一个库）。**Demo 实例**：现在的 `chatbot.acuventech.com`；**生产实例**：承载真实租户。同一镜像，靠启动开关区分 |
| 租户 | 用 Chatbot 服务自己顾客的一方。Acuven 是生产实例上的一个租户；Demo 实例上的行业演示、网店样板各是 Demo 租户 |
| 渠道 | 顾客找来的入口：一个 WhatsApp 号，或一个网站上的聊天窗口 |
| 机器人 | 人设、知识、模型、可用能力的一套配置。一个渠道接一个机器人（Demo 的 demo 号例外：菜单选行业） |
| 业务系统 | 按接入契约开放能力的系统（网店、CRM、ERP、Stock Core…） |
| 能力 | 业务系统开放的一项操作，带风险级别与是否需要顾客身份 |
| 顾客 | 终端顾客，在渠道上与机器人对话的人 |
| 同事 | 租户这边接手对话的人工客服 |
| 有权人员 | 业务系统里有权批准某项高风险写入的人（E-05） |

## 5. 需求（E-21 ①～⑧ 逐条）

每条给出编号与验收方法。「真机」指用真实手机在 WhatsApp 里操作，Claude 做不了，须由 Kelvin 或同事完成（本仓库 `tasks/todo.md` 约定第 5 条）。

### ① 渠道与网页聊天窗口都要，同一个客服、同一份对话记录

| 编号 | 需求 | 验收 |
| --- | --- | --- |
| R-1.1 | 支持 WhatsApp（Cloud API 号与 coexistence 号）和网页聊天窗口两类渠道；渠道类型可扩展（现有企业微信代码保留但不在本次范围，见 Q-18） | 两类渠道各配一个，在同一租户下收发成功 |
| R-1.2 | 同一租户的不同渠道可以接同一个机器人：同一套人设、知识、能力，回答口径一致 | 同一问题分别在 WhatsApp 与网页窗口问，答复依据相同（允许措辞不同） |
| R-1.3 | 所有渠道的对话写进同一个对话存储（同一张表、同一查询方式）；人工接手界面与导出都能按租户查到全部渠道的对话 | 网页与 WhatsApp 各聊一段，在工作台或导出里同一处查到两段 |
| R-1.4 | 同一顾客在不同渠道的对话**只有在核验到同一个业务系统顾客后**才归到同一顾客名下；手机号相同不自动归并（B-05）。归并后人工接手界面里显示在一起；机器人上下文是否跨渠道延续见 Q-04 | 未核验时两段分开；核验到同一系统顾客后显示在一起；号码相同但未核验时不归并（自动化测试） |

### ② 三种交付形态，Acuven 是其中一个租户

| 编号 | 需求 | 验收 |
| --- | --- | --- |
| R-2.1 | 多租户 SaaS、Acuven 托管专属、客户自托管用**同一份代码、同一镜像**；形态差异只在配置与部署（A-01、C-14） | 代码里没有按形态分叉的分支（审查）；专属实例用生产镜像加独立配置能起来 |
| R-2.2 | Acuven 是生产实例上的普通租户，没有专属代码路径；租户类型只影响计费模式（自用租户只计量不扣费，见 DESIGN §10） | 审查：没有 `if tenant == acuven` 一类判断 |
| R-2.3 | 租户之间数据隔离：对话、顾客、配置、密钥、用量都按租户隔离；两个租户里出现同一手机号时互不可见 | 自动化测试：两租户同号码，各自只看到自己的对话与状态 |
| R-2.4 | 专属、自托管实例与多租户实例之间不直接互通；客户机器不接成 SaaS 租户（C-14）。WhatsApp 号在专属/自托管下怎么接 Meta 见 Q-10，计费见 Q-11 | 阶段 3 验收时按 Q-10、Q-11 的决定补具体验收 |

### ③ 能力可配置，高风险写入须人确认

| 编号 | 需求 | 验收 |
| --- | --- | --- |
| R-3.1 | 每个业务系统用能力清单声明自己开放什么：名称、说明、输入格式、风险级别（只读 / 低风险写入 / 需人确认）、是否需要顾客身份（契约 §3） | 网店样板的清单通过 Chatbot 的清单校验 |
| R-3.2 | 每个租户对每个已接入系统的每项能力可单独打开或关闭；可以把一项能力收紧（例如低风险写入改为需人确认），不能放宽系统声明的级别 | 自动化测试：关掉的能力不出现在模型可用工具里；收紧后走确认流程 |
| R-3.3 | 机器人实际能用的能力 = 系统声明 ∩ 租户打开 ∩ 该机器人配置 | 自动化测试 |
| R-3.4 | 「需人确认」的写入，机器人只能**提出**，展示具体变更，由业务系统里的有权人员确认后才执行（E-05）；谁确认、在哪确认见契约 §5 与 Q-07 | 网店样板：退款申请经机器人提出后，后台批准前不生效 |
| R-3.5 | 租户收紧或关闭能力立即生效（下一次模型调用即按新配置），并留下谁、何时、改了什么的记录（E-05） | 自动化测试 + 查记录 |
| R-3.6 | 模型只提出调用，由应用执行；租户、会话、顾客身份由服务端注入，模型不能填；写入带来源与幂等键（E-04） | 契约 §4 的保留字段校验测试；重放同一幂等键不重复执行 |

### ④ 三种人工接手，按客户选

| 编号 | 需求 | 验收 |
| --- | --- | --- |
| R-4.1 | 支持三种接手方式：手机 WhatsApp Business App（coexistence 回音）、CRM 收件箱（J-04）、Chatbot 自带工作台 | 每种至少一个渠道真机或端到端验收（阶段见 DESIGN §12） |
| R-4.2 | 接手方式按客户选；选的粒度（按租户还是按渠道）见 Q-03 | 按 Q-03 决定补 |
| R-4.3 | coexistence 号上，同事在手机 App 发出的消息**一律**让 AI 让位，不论该渠道选的接手方式是什么（这是号码本身的事实） | 真机：同事在 App 回复后，顾客下一条消息 AI 不回 |
| R-4.4 | 接手中 AI 不回复，顾客消息照常记录并送到接手方；接手结束（超时、同事交还、指令）后 AI 恢复 | 自动化测试覆盖三种结束方式 |
| R-4.5 | 自带工作台只做：看对话、接手、回复、交还。**不做**工单、指派规则、状态流转、SLA（A-15） | 审查：无工单相关数据表与界面 |
| R-4.6 | 三种方式共用一个接手状态（同一对话同一时刻只有一个状态），换方式不改状态机 | 自动化测试 |

### ⑤ 顾客身份

| 编号 | 需求 | 验收 |
| --- | --- | --- |
| R-5.1 | 网页聊天窗口：以顾客在宿主系统**已登录**的身份为准，由宿主系统后端签发短时效身份令牌（契约 §6.1）；没有令牌的是匿名访客 | 网店样板：会员登录后能查自己的订单；伪造、过期、别的网站签的令牌被拒 |
| R-5.2 | 匿名访客与未核验的渠道顾客只能用「不需要顾客身份」的能力 | 自动化测试 |
| R-5.3 | 渠道（WhatsApp）上须先核验才能用需要顾客身份的能力；核验方式由业务系统提供（契约 §6.2，Q-05） | 网店样板：未核验时查订单被引导去核验 |
| R-5.4 | 核验只在本次对话有效，过期即失效（Q-06）；手机号或聊天身份相同不自动认人、不授予订单访问（B-05） | 自动化测试：过期后需重新核验；换对话需重新核验 |
| R-5.5 | 身份由服务端注入能力调用，模型无法指定或改写（E-04） | 契约 §4 校验测试 |
